# ADR 0011 — Client-side i18n: i18next, pt default, cookie preference behind a storage seam

**Status:** Accepted · **Date:** 2026-08-09

## Context

The build plan always called for **"pt-PT primary with en fallback from the
first screen"** — retrofitting i18n later costs weeks, not hours, once every
component has hand-written copy baked in. The I0 `pos` shell was built with
exactly that hand-written copy (a mix of Portuguese and English strings) to
get the walking skeleton demoable fast. This ADR is that retrofit, done now
— at I0, with one screen — rather than later, with four client apps and
hundreds of strings.

Two explicit requirements shaped the decision: the language choice must
**persist in a cookie**, and the design must **not assume web** — Android and
iOS clients are coming (ADR 0007, ADR 0008), and neither has a browser
cookie jar.

## Decision

**i18next + react-i18next**, resources for `pt` (default) and `en`, with
language *persistence* kept in a separate module from language
*configuration*.

### Why i18next over alternatives

- It is framework-agnostic at its core (`i18next`) with bindings for React
  (`react-i18next`) today and React Native (`react-i18next` also supports RN,
  or the core library directly) later — the same resource files and the same
  `t()` call shape carry over to a native client without a rewrite.
- Web-only alternatives (e.g. `next-intl`) would have to be replaced, not
  extended, when a mobile client is built — exactly the retrofit this ADR
  exists to avoid.

### The storage seam

```
src/i18n/
  languageStorage.ts   LanguageStore interface + cookieLanguageStore (web)
  i18n.ts              i18next config — reads/writes only through the interface
  resources/pt.ts       resources/en.ts
```

`LanguageStore` is two methods, `get()` and `set(language)`. `i18n.ts` never
touches `document.cookie` directly — it calls `cookieLanguageStore`, which is
the only place that does. A React Native client implements the identical
interface backed by `AsyncStorage` or `SecureStore`, swaps it into `i18n.ts`,
and every component, every resource file, and every `t()` call in the app is
unchanged. This is the same shape as `IFiscalProvider` (ADR 0002) and
`IClock` — one interface, swappable implementation, business logic that
never notices which one is live.

### The cookie itself

`brasa.lang`, value `pt` | `en`, `Path=/`, `Max-Age` one year, `SameSite=Lax`,
`Secure` when served over HTTPS. Set and read entirely client-side via
`document.cookie` — **never sent to or read by the API.** This is a
UI-rendering preference, not a credential, and does not conflict with
**ADR 0008 (no cookie auth)**: that ADR is about authentication cookies
specifically. A preference cookie the API never sees carries none of the
risks — CSRF, native-client incompatibility — ADR 0008 exists to avoid.

### What is, and is not, translated

Translated: UI chrome — labels, buttons, headings, empty states, static
copy. Every string in `resources/pt.ts` / `resources/en.ts`.

**Not** translated by this mechanism:

- **Menu item and category names.** These are tenant business data from the
  database (`MenuItem.Name`), not UI copy. Translating a dish name is a
  data-modelling problem (per-locale content) for `CAT` to solve later if a
  tenant ever wants it, not something a UI i18n library does.

  **Table labels are the one deliberate exception to "seeded data stays
  untranslated."** `Table.Label` looks like the same category as
  `MenuItem.Name` — also a seeded database string — but a dish name carries
  real culinary identity worth preserving ("Bacalhau à Brás" translated
  would misrepresent the food), while "Mesa 1" is just a generic word plus a
  number, and floor/kitchen staff who don't read Portuguese still need to
  recognise which table is which. `src/lib/tableLabel.ts` renders it as
  "Table 1" in English (data untouched, display-only), and the takeaway
  ticket's blank-label default is sent by the *client* in the UI's own
  language (`floor.takeawayDefaultLabel`) rather than relying on the API's
  hardcoded Portuguese default ("Levantamento") leaking through. If a future
  tenant-entered table label doesn't match the seeded `"Mesa N"` shape, it
  passes through unchanged — the same as any other real tenant content.
- **Money formatting.** `formatMoney` (`src/lib/money.ts`) is hardcoded to
  `Intl.NumberFormat('pt-PT', ...)` regardless of the UI language toggle,
  deliberately. A total shown to a guest, or printed on a receipt, must not
  change format because a staff member switched their own interface to
  English. This is the same category of decision as gross-first VAT
  (`docs/fiscal/README.md`) — a fiscal/business-correctness concern, not a
  presentation one.
- **The receipt's issued timestamp** — same reasoning, same hardcoded
  `'pt-PT'`, see the comment in `Receipt.tsx`.
- **Server-sent error text — partially fixed.** `ProblemDetails.title`
  still comes from the API in English (`Error.Description`), but `pos` no
  longer shows it verbatim: `describeError()` (`App.tsx`) looks up
  `Error.Code` — the stable, documented contract clients are meant to
  branch on (`docs/architecture/api-contract.md`) — in a `code → localized
  message` dictionary (`error.code.<code>` in `resources/{pt,en}.ts`,
  nested to match the code's own dots, e.g. `error.code.floor.table_not_dirty`)
  first, falling back to the raw English message (with the code shown
  alongside, for support purposes) only when no entry exists yet for that
  code. This is real, ongoing work — every new error code needs an entry in
  every supported language, same as any other UI string — so it's scoped
  deliberately: the ~20 codes `pos`'s own API calls (`src/api/client.ts`)
  can actually trigger are covered; codes only reachable from `admin` or a
  future client are not yet. An untranslated code is never silently hidden,
  just shown in English with its code visible until someone adds it.

## Consequences

**Good**

- Adding a language is a new `resources/<lang>.ts` file plus one entry in
  `LANGUAGES` (`LanguageToggle.tsx`) — no component changes.
- The mobile retrofit this ADR was written to avoid is now actually avoided:
  swap one file (`languageStorage.ts`'s implementation), not four apps' worth
  of hardcoded strings.
- Verified end-to-end, not just built: `src/web/e2e/tests/language-toggle.spec.ts`
  checks the rendered UI, the cookie's actual attributes (`Path`, `SameSite`,
  not `httpOnly`), and that it survives a page reload.
- The seam already paid off with a second web client, not just the mobile
  one this ADR anticipated: `admin` (WEB-09) applies the identical shape —
  its own `src/i18n/{i18n,languageStorage}.ts` and `resources/{pt,en}.ts`,
  duplicated rather than shared (see `web/sdk`'s own deferral reasoning in
  `pos`'s `api/types.ts`) — and deliberately reuses `pos`'s exact
  `brasa.lang` cookie name rather than picking its own, so a staff member's
  language choice is one preference across every client on the same host,
  not per-app state. `src/web/e2e/tests/admin-language-toggle.spec.ts`
  verifies it the same way.
- The error-code-to-localized-message dictionary named as future work below
  is now built for `pos`: `error.code.<code>` in `resources/{pt,en}.ts`,
  checked via `i18n.exists()` in `describeError()`. Verified live in a real
  browser in both languages, not just built:
  `src/web/e2e/tests/error-localization.spec.ts` triggers a genuine 409
  (`catalog.item_unavailable` — 86ing an item after the menu has already
  rendered, a realistic multi-terminal race, not a contrived one) and
  asserts the exact rendered text in each language.

**Bad**

- Error messages are only localized for the ~20 codes `pos`'s own API
  calls can trigger — codes only reachable from `admin` (or a future
  client) still show the raw English server message. `admin`'s equivalent
  dictionary hasn't been built yet.
- `{{count}}` interpolation (`order.covers`) has no real plural handling —
  acceptable for a cover count that is almost always ≥ 2, worth revisiting
  if a language with stricter plural rules is ever added.

## Revisit when

- A React Native client is scaffolded — implement `LanguageStore` there and
  confirm nothing outside `i18n.ts` needed to change.
- Menu content itself needs per-locale translation — that's a `CAT` data
  model change, not an extension of this mechanism.
- ~~The error-code-to-localized-message dictionary is built — update this
  ADR to record where it lives.~~ Done for `pos` — see "Consequences"
  above. `admin` needs the equivalent `error.code.*` dictionary and
  `describeError()`-style lookup built into its own error handling next.
